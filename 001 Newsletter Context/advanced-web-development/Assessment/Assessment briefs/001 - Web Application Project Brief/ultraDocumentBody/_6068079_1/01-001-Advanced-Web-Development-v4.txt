Specification

Overview

Build a full-stack, secure Content Management System (CMS) for managing and
publishing newsletters using Next.js (App Router), PostgreSQL with Prisma ORM,
and Auth.js (or custom authentication).


Description

Building a Secure Newsletter CMS. In this assignment, you will build a secure, full-
stack Content Management System (CMS) that allows users to register accounts, log
in, create, draft, schedule, and publish newsletters.
The primary goal of this assignment is to demonstrate a strong authentication system
with solid user session state management. You will design an authorisation
architecture for all users of the system. Public and private facing is core. You must be
able to demonstrate that public routes are for the public while private ones can only
be accessible to eligible users. Security features are the core interests of this
assignment, for example, routes are guarded using Next.js Middleware. We will be
looking closely the solutions you have implemented to cyber defence. These security
features must not be comprising usability features, however. This assignment includes
minimum requirements and desirable requirements. Marks are awarded according to
the quality of your solutions.

Topic Focus: Next.js App Router, PostgreSQL with Prisma ORM, Auth.js / Custom Auth
Systems, Middleware Protection

Technical Stack Requirements
   •   Language: TypeScript
   •   Framework: Next.js
   •   Database & ORM: PostgreSQL + Prisma ORM
   •   Authentication: Auth.js (Credentials or Google OAuth Provider) OR Custom
       Credentials (JWT in HTTP-only cookies)
   •   Styling: Tailwind CSS and DaisyUI

Note: You may be penalised if a tech stack other than listed above is used.

Minimum Technical Requirements (50%):

   1. User Registration
         a User Registration (/register): The application must support new user
            registration. A guest user can create an account with an email,
            password, and optional name.
         b Passwords and its management must be strong and secure.
   2. System Security & Route Guarding
         a. Authentication: Implement authentication using Auth.js or a Custom
            Credentials approach. Logout must also taking care of active session
            cookie, application state, and redirect the user appropriately.
         b. A strong and robust sessions management design architecture
            implemented
         c. End Points: all end points must be secure. The /dashboard route
            and any sub-routes (e.g., /dashboard/create,
            /dashboard/edit/[id]) must be strictly protected. Unauthenticated
            attempts to access /dashboard must not be allowed.
         d. Public Access: whole site apart from dashboard (i.e. no authentication
            required)
         e. Private Access: user dashboard
                   i. The link to /dashboard must only be visible in the navigation
                      bar when a user is authenticated.
        f. Navigation:
                   i. For authenticated users:
                         1. The /login and /register links are hidden
                         2. Their name or email display in the Navbar
                         3. A functional logout button is available for them
                  ii. For public users:
                         1. They can access all public areas of the app.
                         2. /login and /register links are available for them.
  3. Database Schema (Prisma & PostgreSQL)
        a User Model: Stores user credentials (hashed password) or OAuth
            profile details (id, email, name, password, createdAt, updatedAt).
        b Newsletter Model: Linked to the User model via a 1-to-Many
            relationship (User -> Newsletter). Must include:
                i. id (Primary Key)
               ii. title (String)
              iii. content (Text)
             iv. image (Text)
               v. status (Enum or String: "Draft", "Schedule", or "Sent") —
                      Default: "Draft"
             vi. authorId (Foreign Key referencing User)
             vii. createdAt & updatedAt (Timestamps)
  4. Protected Dashboard (http://localhost:3000/dashboard)
        a User Isolation: The dashboard must only show newsletters created by
            the logged-in user. Users must never view, edit, or delete another
            user's newsletters.
        b CRUD Operations: Provide an explicit button to "Create Newsletter".
            Support Viewing, Editing and Deleting existing newsletters.
        c Status Updates: Allow updating a newsletter's status between "Draft",
            "Schedule", and "Sent", as well as editing the existing Newsletter
        d Newsletters with a status of “Sent” are considered public, and be feed
            to public Newsletter page automatically
  5. Public Newsletter Page (http://localhost:3000/newsletters)
        a Displays a public feed of newsletters.
        b You can use open-source image (https://unsplash.com) for the
            newsletter
        c Filtering: Must ONLY render newsletters where status === "Sent".
            Drafts and scheduled posts must remain invisible to the public.




Desirable Technical Requirements (25%)
   1. Support multiple authentication methods
   2. 2-Factor authentication
   3. Password-less authentication
   4. Role-based Authorisation. Roles can be admin or moderator.
   5. Public newsletter page includes a feed from https://us-
      rse.org/api/newsletters.json or articles https://dev.to/api/articles or
      https://daringfireball.net/feeds/json
   6. Users can interact with each of the public newsletter – like, comment, share.
   7. Usability features to help with the interactions of the app.
